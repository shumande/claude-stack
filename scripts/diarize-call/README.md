# diarize-call — разбор звонка по голосам, локально

Проверено 15.09.2026 на реальном 50-минутном двухголосом звонке (`Alexandr.m4a`) — работает.
Не переделывать заново без причины, только докручивать. Что именно проверено — см. секцию
«Докручено 15.09.2026» ниже: три ручных шага прогонялись на реальных данных отдельно;
единый `diarize_call.py` объединяет их тем же способом, но целиком (включая сам вызов
`diarize.py` с реальным HF_TOKEN) в этой сессии не перепрогонялся — токена под рукой не было.

## Зачем

Spokenly (macOS-приложение, стоит локально) умеет распознавать речь бесплатно и быстро,
но разделение говорящих (diarization) у него — только в Pro-подписке. Вместо покупки:
берём открытую модель `pyannote/speaker-diarization-community-1` (GitHub `pyannote/pyannote-audio`)
для вопроса «кто когда говорит», и уже готовый локальный Spokenly — для вопроса «что сказано».
Всё бесплатно, всё своё, ничего никуда не уходит.

## Что нужно один раз

1. `pip install pyannote.audio` (torch уже должен быть — обычно стоит из других AI-проектов).
2. Аккаунт на huggingface.co → принять условия модели
   [pyannote/speaker-diarization-community-1](https://huggingface.co/pyannote/speaker-diarization-community-1)
   («Agree and access repository»).
3. Токен: [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens) (read-доступа хватит).
   **Постоянное место — `~/.secrets/huggingface.key`** (chmod 600, только сам токен внутри,
   без переносов строк) — тот же принцип, что у `~/.claude/scripts/openrouter-key.sh` для
   OpenRouter. Не коммитить, не класть в код/конфиги. Разово можно и через
   `HF_TOKEN=hf_xxx` в окружении — `hf_token.py` проверяет сначала файл, потом переменную.
4. Spokenly должен быть запущен (обычный фоновый процесс приложения).

## Запуск — один вызов

```bash
python3 diarize_call.py /path/to/call.m4a --speakers "SPEAKER_00=Алексей,SPEAKER_01=Клара"
```

Собирает все три шага ниже + склейку соседних реплик одного спикера + сборку
итогового `<call>.diarized.md` (имя, таймкод, текст). Флаги: `--out`, `--work-dir`,
`--keep-work` (не удалять клипы) — см. `--help`. Обёрнуто скиллом
[`~/.claude/skills/diarize-call/`](~/.claude/skills/diarize-call/SKILL.md) — доступен
глобально во всех окнах.

## Пайплайн вручную (3 шага — на случай отладки одного шага отдельно)

```bash
# 1. Диаризация — кто когда говорит (даёт .segments.json рядом с исходником)
python3 diarize.py /path/to/call.m4a

# 2. Нарезать аудио по отрезкам (manifest.json с абсолютными путями клипов)
python3 extract_clips.py /path/to/call.segments.json /tmp/call_clips

# 3. Распознать каждый отрезок отдельно (напрямую через локальный порт Spokenly,
#    минуя ручные вызовы MCP-инструмента по одному — иначе на длинном звонке
#    получаются сотни отдельных вызовов)
python3 transcribe_all_segments.py /tmp/call_clips/manifest.json /tmp/call_transcribed.json
```

`diarize_call.py` — тот же пайплайн, просто одним вызовом; финальную склейку и .md
делает сам (`merge_adjacent` + `render_markdown`), не нужно собирать руками.

## Важные грабли (уже пойманы, не наступать снова)

- **torchcodec на macOS сломан** («Could not load this library: .../libtorchcodec_image.dylib»).
  `diarize.py` уже обходит это — грузит аудио через `soundfile` в память и передаёт pyannote
  словарём `{"waveform": tensor, "sample_rate": int}`, а не путём к файлу. Если ошибка вернулась —
  чинить тем же способом, не гнаться за починкой torchcodec напрямую.
- **Склейка нескольких отрезков в один файл с паузами между ними НЕ работает** — Spokenly не
  режет по вставленной тишине, отдаёт весь файл одним куском текста без внутренних таймкодов.
  Проверено, не тратить время на эту идею снова. Только по одному отрезку на файл.
- **Spokenly слушает `localhost:51089`** и принимает обычный JSON-RPC (MCP-протокол) через
  `curl -X POST`. `mcp-bridge.sh` в `~/Library/Application Support/Spokenly/` — просто прокладка
  между stdin и этим портом. Так и вызывается напрямую в `transcribe_all_segments.py`.
- **Относительные пути до клипов не находятся** — Spokenly-приложение резолвит их не от cwd
  скрипта. Всегда абсолютные пути (`extract_clips.py` уже это учитывает).
- Метки `SPEAKER_00`/`SPEAKER_01` от pyannote не именованы — сопоставлять с реальными людьми
  нужно по опорным фразам в тексте (упомянутое имя, характерная фраза), не наугад. Самые первые
  1-2 реплики короткого приветствия в начале звонка — зона риска (модели не хватает аудио на
  разогрev), доверять чуть меньше, чем середине разговора.

## Докручено 15.09.2026 (второй заход)

- Три ручных шага собраны в `diarize_call.py` — один вызов, на выходе готовый .md.
- Оформлено как глобальный скилл `~/.claude/skills/diarize-call/` (не плагин claude-stack —
  инструмент личный, завязан на локально стоящий Spokenly, не продуктовый плагин вроде
  dsgvo/kmu; прецедент двойного размещения, как у agent-council, тут не подошёл: этому
  инструменту нечего показывать в маркетплейсе).
- `HF_TOKEN` — постоянно в `~/.secrets/huggingface.key` (см. выше), не в shell-профиле:
  так короче путь поиска и не светится в `env`/истории шелла при случайном `printenv`.

### Что реально перепроверено в этот заход (а что нет)

Шаги 2 (`extract_clips.py`) и 3 (`transcribe_all_segments.py`) прогнаны заново на реальных
210 отрезках того же 50-минутного звонка через настоящий Spokenly — результат слово-в-слово
совпал с ранее одобренным текстом. Новая склейка (`merge_adjacent`) и рендер (`render_markdown`)
юнит-тестированы на граничных случаях (пауза длиннее `MAX_MERGE_GAP`, нераспознанное
вклинивание другого спикера между репликами первого) и прогнаны на тех же реальных 210
отрезках. Ревью нашло и это исправило: без разрыва по чужому вклиниванию склейка стирала
16 из 63 реплик, ошибочно сшивая их через незамеченные бэкчаннелы («ага» и т.п.) второго
спикера — так делать было нельзя, реплики теперь не сшиваются через любое, пусть и
нераспознанное, чужое высказывание.

Не перепрогнан целиком через `diarize_call.py`: сам шаг 1 (`diarize.py` — вызов pyannote
с HF-авторизацией и загрузкой модели) — в сессии не было `HF_TOKEN`. Код шага не менялся,
кроме загрузки токена (`hf_token.py`, тоже проверена изолированно), но собственно проводку
через оркестратор целиком на реальном звонке ещё стоит один раз проверить при первом
живом запуске.
